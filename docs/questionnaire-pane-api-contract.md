# Questionnaire-pane tools — API contract (CRL emit home)

**Status:** the authoritative interface the CRL MCP/CLI will expose for the MV PlanDefinition-Questionnaire pane.
The pane session builds the renderer + a fixture against THIS; the CRL side implements the producer + tools after
#189's case-feature emit stabilizes (see "Timing"). Assessed from the pane session's proposal
(`E:\src\mv-plandefinition-questionnaire\docs\mv-questionnaire-pane-api.md`, disc-context 2026-08-16).

## Pipeline (fixed)
```
qa case data ─► CRL emit (PlanDefinition + Library + case-feature StructureDefinitions + CodeSystem + ActivityDefinition)
             ─► $apply-driven PRODUCER (JVM: cqf-fhir-cr-cli) ─► Questionnaire + QuestionnaireResponse (answers populated)
             ─► these two TOOLS read ─► pane renders (LForms)
```
Questionnaires are **generated by `$apply`, never emitted from CRL** — no Questionnaire ever appears in `src/fhir/`.
The pane renders only; it never runs `$apply`, spawns a JVM, or reasons about which concepts become fields.

## The ONE decision that fixes `get_case`'s nature (settle before the CRL side implements)
`get_case` is either a **disk read** (the producer flattened the case to one complete Q+QR at build time) or a
**live `$apply`** (run on demand with the current answer state). This hinges on the pane's interaction model:
- **Per-case selection** (each tree/CEL node = a whole case) → build-time flatten, `get_case` reads disk. The
  producer drives `$apply` to the leaf (multi-call — `$apply` reveals one tree level per call — accumulating every
  level into one Questionnaire with a fully-answered QR). **Simplest; no JVM in the MCP server.**
- **Intra-form adaptive reveal** (answering a question surfaces the next level — the DTR behavior) → `get_case`
  must RUN `$apply` on demand → the **MCP server carries a JVM + the cqf jar at runtime** (the §6 jar-distribution
  problem becomes live). The args would grow a current-answer-state / node parameter.

**The signature + return shape above are stable EITHER WAY** — the pane can build against them now. Only the
tool's implementation (read vs run) and one possible extra arg change. Default assumption unless the pane session
says otherwise: **per-case / build-time flatten / disk read.**

## #189-gated fields (do NOT freeze against current emit)
- **`lane` (`local`|`source`|`mixed`) + `laneMatchesArtifact`.** This is a NEW emit-side marker that does not exist
  today. Its semantics are exactly what #189 is reshaping: post-flip the Inferred determination reads BOTH the
  local (`code is`) and record/source (`coded from`) retrieves and MERGES them (dedup + recency), so "the artifact
  expects ONE lane" does not hold cleanly and `laneMatchesArtifact` must be re-grounded against the merged model.
  The CRL side will design + emit a principled lane/provenance marker alongside the source-representation half of
  the flip. Until then, treat these fields as present-but-provisional (a case's data-lane vs the retrieve is a
  useful mismatch signal; the exact enum + rule will settle with the emit). The recency-merge case the pane doc's
  §5 pins (`Age Twenty One Or Older`, both-rep local Observation + Patient birthDate) is the canonical example and
  is correctly understood.
- **The Questionnaire → item mapping** (which case features become which items) is a function of the emitted
  case-feature StructureDefinitions + decision tree, which #189 slices 2b/2d are still moving. The ACCESS
  mechanism is stable; the CONTENT stabilizes after the flip.

## Access mechanism (stable)
The producer runs `PlanDefinition/$apply` (cqf-fhir-cr-cli harness) against the emitted PlanDefinition canonical +
the case's patient bundle (`tests/data/fhir/patient`, the CEL-emitted case data). For the flatten-to-leaf
variant it drives the reveal loop to completion. Case identity key = `libraryId` + `caseSlug` (the tool owns
path resolution; the pane never sees a path). Built Q artifacts land in the sibling results tree
(`tests/results/fhir/patient/<compartmentId>/`), which the tool hides from the pane.
