# Requirements for AI-Assisted CRL Lexer and Parser Development

## Project Overview
CRL is a domain-specific language with **Python-like indentation rules**, meaning that leading whitespace determines block structure instead of explicit braces. The project uses **ANTLR4** (with TypeScript target) for parsing and a **custom lexer** to handle indentation-sensitivity. We aim to develop a robust lexer and parser (and eventually a compiler) for CRL, leveraging AI assistance to speed up development and ensure quality. The grammar (defined in `src/grammar/CRL.g4`) has recently been updated, so tests and lexer logic must be adjusted accordingly. All development is in TypeScript, with **Jest** for testing.

**Goals:** Ensure the lexer emits correct tokens (especially `INDENT`/`DEDENT` for block control), integrate these tokens with the ANTLR parser, and maintain comprehensive tests. We will use AI tools (like code generation assistants) to help with tasks such as refactoring tests, generating token streams, and proposing new test cases, while carefully validating AI contributions.

## File Organization and Generation Workflow
- **Grammar Definition:** The CRL grammar is defined in `src/grammar/CRL.g4`. This combined grammar includes parser rules for language constructs and placeholder lexer rules for tokens (like `INDENT` and `DEDENT`)&#8203;:contentReference[oaicite:0]{index=0}. The grammar should be the single source of truth for language syntax; any changes to syntax (keywords, structure) must be reflected here.
- **Custom Lexer Code:** A custom TypeScript lexer implementation resides in `src/lexer/` (e.g., `CRLLexer.ts`). This lexer is responsible for handling indentation logic that ANTLR’s autogenerated lexer cannot easily do. The team runs `npm run generate` to regenerate ANTLR files **except** the lexer – meaning the ANTLR parser (`CRLParser.ts` and related files under `src/parser/`) is updated from the grammar, but the custom lexer code is maintained manually and not overwritten. We must ensure the generation script or ANTLR configuration does not clobber our custom lexer (for example, by using a separate lexer grammar or disabling the default lexer generation as needed).
- **Generated Parser Files:** The ANTLR TypeScript target will produce parser classes (e.g., `CRLParser.ts`, context classes, and possibly a lexer base class if not suppressed). These go into `src/parser/`. We should integrate our custom lexer with the generated parser. For instance, if using ANTLR’s runtime, after generation we might have an autogenerated `CRLLexer.ts` which we will either replace or subclass with our custom implementation. All token type definitions (enums or constants for `INDENT`, `DEDENT`, etc.) must remain consistent between the grammar and the custom lexer so that the parser recognizes tokens emitted by the custom lexer.
- **Test Files Location:** Tests are organized alongside the code for clarity. Lexer tests are in `src/lexer/` (e.g., `CRLLexer.test.ts`) and parser tests in `src/parser/CRLParser.test.ts`. This co-location helps keep tests relevant to the module they verify. We will maintain this structure: as new features are added to the lexer or parser, create or update corresponding test files in the same directory.
- **Example CRL Programs:** Example source files (valid CRL scripts) are stored in `src/examples/`. These serve as real-world cases to test the parser (and later the compiler). The test suite or development scripts should use these examples to ensure the end-to-end parsing works as expected. For instance, we might have an integration test that tries to parse each example file and verifies no errors are thrown and that the parse tree matches expected structures.
- **Build and Generation Process:** Document and automate the steps to update the language:
  - When grammar rules change, run `npm run generate` to regenerate parser code (with ANTLR4). Ensure the `tokenVocab` or similar options are set if using a separate lexer grammar&#8203;:contentReference[oaicite:1]{index=1} so that the parser knows about tokens defined for the lexer. 
  - After generation, rebuild the project and run tests (`npm test`) to catch any integration issues between the updated grammar and the custom lexer.
  - The **AI assistant** can be involved here by analyzing diffs in the grammar and suggesting updates in lexer logic or tests needed to accommodate the changes.
- **Source Control:** All source files (grammar, custom lexer, tests, examples, generated parser code) should be under version control. The generated parser code can be committed for transparency, but we must be cautious to regenerate it when grammar changes to avoid drift. Consider adding a CI check that fails if the grammar file has changes that aren’t reflected in the generated parser (to enforce running the generator).

## Lexer Implementation Requirements
The custom lexer is a critical component that must interpret leading whitespace to produce `INDENT` and `DEDENT` tokens in the token stream, in addition to regular tokens (keywords, strings, etc.). The lexer’s behavior should be carefully defined as follows:

- **Indentation Handling:** Implement logic to track the current indentation level (e.g., using a stack of indent lengths&#8203;:contentReference[oaicite:2]{index=2}&#8203;:contentReference[oaicite:3]{index=3}). On encountering a newline (`\n` or `\r\n`, which is a `NEWLINE` token in the grammar), the lexer should look at the sequence of spaces (and tabs, if allowed) at the start of the next line:
  - If the new line’s indent is deeper (more spaces) than the previous line’s indent, that signifies a new block. The lexer must emit an `INDENT` token *before* emitting the first non-whitespace token of the new line&#8203;:contentReference[oaicite:4]{index=4}. The indent length is typically pushed onto the indent stack.
  - If the new line’s indent is shallower (fewer spaces), that signifies closing one or more blocks. The lexer must emit one or more `DEDENT` tokens *before* emitting the next line’s first token, popping indent levels from the stack for each `DEDENT`&#8203;:contentReference[oaicite:5]{index=5}. For example, if indent level decreased from 8 spaces to 4 spaces, one `DEDENT` should be emitted (assuming 4 spaces per indent level). If it decreased from 8 to 0, two `DEDENT` tokens would be emitted in sequence to close two blocks. (The parser grammar is written to expect matching INDENT/DEDENT pairs around block constructs.)
  - If the indent length is the same as the previous line, no indent or dedent token is produced (the new line continues at the same block level).
- **Fixed Indent Unit:** Enforce a consistent indent unit of 4 spaces for CRL. The grammar indicates that one indent level is exactly four spaces&#8203;:contentReference[oaicite:6]{index=6}. The lexer should either **reject** indentations that are not a multiple of 4 or treat them as errors. All indents must align to this 4-space grid. This means:
  - The first time an indent is encountered, we know it should be 4 spaces (or a known multiple if we allow multiple levels jump). We can set the expected indent unit to 4&#8203;:contentReference[oaicite:7]{index=7}.
  - If a line is indented by, say, 6 spaces (which is not a multiple of 4), the lexer should throw a clear error or emit a special error token indicating a misaligned indent. Similarly, if a dedent does not exactly match a previous indent level (a "half-dedent" scenario), that’s an error&#8203;:contentReference[oaicite:8]{index=8}.
  - Optionally, we might allow tabs or a different indent size in the future via configuration, but for now indent size is fixed. This simplifies the implementation.
- **Token Emission Order:** Ensure `INDENT`/`DEDENT` tokens are inserted into the token stream in the correct order relative to other tokens&#8203;:contentReference[oaicite:9]{index=9}. Specifically, an `INDENT` should appear right after the newline that starts a new block and before the first token of the indented block. Conversely, a `DEDENT` should appear right before the first token of the line that closes a block (or possibly right after a preceding newline).
  - The lexer may need to **peek** at the next character after a newline to determine indent changes *before* deciding what token to emit next. This might require buffering whitespace or implementing `nextToken()` logic that can emit multiple tokens (e.g., a `NEWLINE` token followed by an `INDENT` or `DEDENT` sequence, then the next significant token).
  - The ANTLR runtime typically allows emitting multiple tokens or adjusting the input index without consuming everything at once – our implementation can utilize such techniques or manage its own buffer of pending indent/dedent tokens.
- **Skipping Whitespace & Comments:** The lexer should skip irrelevant whitespace **except** for indentation. In practice:
  - Any spaces or tabs **after** the first non-whitespace character of a line (i.e., internal to a line) can be tokenized as `WS` and skipped (as per grammar rule `WS: [ \t]+ -> skip;`)&#8203;:contentReference[oaicite:10]{index=10}. Only leading whitespace at line start is significant for indent logic.
  - Comments (`// line comments` or `/* block comments */`) should be skipped entirely&#8203;:contentReference[oaicite:11]{index=11}. The presence of a comment on an otherwise blank line should likely not produce indent changes. (E.g., an indented line that only contains a comment might be tricky: we should decide whether to treat it as an empty line or maintain indent context. A sensible approach is to treat it as an empty line – i.e., emit a `NEWLINE` but no indent/dedent changes, similar to how Python ignores comments in indentation.)
  - Blank lines (lines that are empty or only whitespace) should not affect indent level. The lexer can treat a blank line as producing a `NEWLINE` token but then immediately ignore any indent difference (since the line has no content). Alternatively, the lexer could skip over blank lines entirely (not even emitting NEWLINE) to avoid confusing the parser. However, because the grammar’s `NEWLINE` token is part of the syntax (e.g., separating statements), it might be safer to still emit a single NEWLINE for a blank line but ensure no INDENT/DEDENT is generated. This detail must be handled carefully to avoid parse errors when empty lines appear.
- **End-of-File (EOF) Handling:** When the end of input is reached, the lexer must ensure that all open indentation blocks are properly closed. This means if the indent stack depth is greater than 0 at EOF (we are still inside one or more indented blocks), the lexer should emit a series of `DEDENT` tokens to return to baseline indent (zero) before finally emitting the EOF token&#8203;:contentReference[oaicite:12]{index=12}. This behavior ensures the parser can reduce all open rules and the grammar’s `file` rule, which likely expects an EOF, is satisfied with matching DEDENTs produced. For example, if the file ends while 2 levels deep in indentation, two DEDENT tokens should be output just before EOF. If the indent stack isn’t fully cleared by EOF, that’s a lexing error.
- **Error Reporting:** The lexer should clearly report indentation errors:
  - If an indent or dedent is misaligned (does not match 4-space increments or the previous indent levels on the stack), throw a descriptive error (or emit an error token that the parser can catch). For instance, encountering an indent of 2 spaces when 4 is expected, or dedenting to a level that was never established, should be considered errors. By catching these at the lexing stage, we can provide clearer feedback (“Indentation error at line X”) rather than obscure parser errors&#8203;:contentReference[oaicite:13]{index=13}.
  - The lexer should also handle illegal characters or other unexpected input gracefully, either by skipping or erroring as appropriate, so that the overall system can handle or report all lexing issues.
- **Maintainability and Clarity:** Because this custom lexer logic is complex, it should be well-documented and modular:
  - Ideally implement the indent/dedent handling in a helper or base class (similar to existing solutions like *antlr-denter* or *Dentlr*&#8203;:contentReference[oaicite:14]{index=14}) to keep the code clear. The approach may involve overriding the `nextToken()` method of the ANTLR lexer class to inject indent/dedent logic while largely delegating to the ANTLR-generated rules for other tokens&#8203;:contentReference[oaicite:15]{index=15}.
  - Keep the lexer code **in sync** with grammar definitions. For example, if new keywords or token types are added to the grammar, ensure the lexer knows how to produce them (usually the ANTLR-generated part will handle recognizable literals, but if we add new kinds of whitespace or context-sensitive tokens, update the custom logic accordingly).
  - The lexer's responsibilities should be focused only on correctly tokenizing input. It should not attempt to enforce higher-level syntactic rules beyond tokenization (that’s the parser’s job). For instance, deciding whether a `use` clause is allowed in a certain place should be left to the parser rules, whereas deciding where an `INDENT` token goes is the lexer’s job.
- **AI Assistance for Lexer:** We intend to use AI to assist with lexer development where possible:
  - Use AI to generate **sample inputs** and predict their tokenization for us to verify. For instance, we can prompt the AI with a CRL code snippet and ask what tokens it should produce, then compare to our lexer’s output as a validation.
  - Leverage AI to check edge cases: ask for scenarios that might break the indent logic (such as tricky nested structures, empty blocks, etc.) and ensure our lexer accounts for them.
  - The AI can also help refactor or optimize the lexer code by suggesting clearer logic or catching conditions we might miss. However, all AI-suggested changes must be reviewed and tested by the development team, especially because correctness is critical in lexing.

## Parser Implementation and Integration Requirements
The parser is generated from the CRL grammar and must work seamlessly with the custom lexer. Key requirements for the parser and its integration include:

- **Grammar Rules Coverage:** The grammar currently covers top-level constructs like `decision`, `action`, and `casefeature`, each with their nested sub-rules (e.g., `decisionBlock` with `whenClause`, `whenBlock`, `terminalBlock`, etc.). All these rules and sequences rely on proper placement of `NEWLINE`, `INDENT`, and `DEDENT` tokens to delineate blocks&#8203;:contentReference[oaicite:16]{index=16}&#8203;:contentReference[oaicite:17]{index=17}. We must ensure the grammar is consistent with the intended language:
  - A `decision` must be followed by a newline and an indented block of one or more `when` clauses&#8203;:contentReference[oaicite:18]{index=18}.
  - Each `whenClause` ends with `then NEWLINE` and is followed by either an indented nested block of further conditions or a terminal block of actions&#8203;:contentReference[oaicite:19]{index=19}.
  - The optional qualifiers (`any` or `all`) apply only at the start of an indented group of `whenClause` entries&#8203;:contentReference[oaicite:20]{index=20}. The parser should correctly handle when a qualifier is present by expecting it as the first element in a nested block (and only in that context).
  - Terminal actions (`do` or `use` statements) appear inside a terminal block and each ends with a NEWLINE&#8203;:contentReference[oaicite:21]{index=21}.
  - Blocks are properly closed by `DEDENT` tokens which correspond to an earlier `INDENT`&#8203;:contentReference[oaicite:22]{index=22}. The grammar explicitly uses `INDENT` and `DEDENT` tokens in its production rules to enforce this structure. For example, a `decisionBlock` is defined as `INDENT whenClause+ DEDENT`&#8203;:contentReference[oaicite:23]{index=23}, meaning the parser will expect an `INDENT` token to start the block and a `DEDENT` to end it.
- **Custom Lexer Integration:** The parser must use the **custom lexer’s token stream** instead of any default lexer. This requires integrating the two components in code:
  - When running the parser in tests or in production, instantiate the custom `CRLLexer` with the input text, then feed its tokens into the `CRLParser`. For example, in code: 
    ```ts
    const input = CharStreams.fromString(sourceText);
    const lexer = new CRLLexer(input);  // custom lexer instance
    const tokenStream = new CommonTokenStream(lexer);
    const parser = new CRLParser(tokenStream);
    const tree = parser.file();  // parse according to the 'file' start rule
    ```
    This integration ensures that the parser receives our lexer's INDENT/DEDENT tokens. We need to double-check that our `CRLLexer` outputs tokens with the exact token type IDs that `CRLParser` expects for INDENT/DEDENT (the ANTLR generator will have created token type constants for these, likely based on their order in the grammar).
  - If the ANTLR generation still produces a `CRLLexer` class (with placeholder rules), we have two options: either prevent generation of that class by separating the grammar (using a `tokenVocab` approach&#8203;:contentReference[oaicite:24]{index=24}), or subclass/replace it with our implementation. It’s critical that the `npm run generate` process and our build know to use the custom lexer. We might consider giving our custom lexer a distinct name or namespace to avoid confusion, but it should ultimately implement the ANTLR `Lexer` interface so that `CommonTokenStream` works with it.
- **Parser Expectations for Tokens:** Given the language’s structure, the parser will expect tokens in a certain order. We need to guarantee the lexer provides a stream that meets these expectations:
  - Every `INDENT` token must correspond to a new block where the grammar expects an `INDENT`. Likewise, every emitted `DEDENT` should line up with a grammar rule ending a block. Superfluous or misordered indent/dedent tokens will cause parse errors. The lexer and parser design should ensure that cannot happen for valid code (and for invalid indentation, the lexer’s error will prevent the parser from even running).
  - The parser expects each statement and sub-block to end with a `NEWLINE` (often just before a DEDENT). The lexer should not drop required newline tokens. Each `NEWLINE` in the input should appear in the token stream (except perhaps trailing newlines or blank lines as discussed) so that the parser can count them. The grammar uses `NEWLINE` tokens to separate statements and to detect line breaks after `then` and after actions&#8203;:contentReference[oaicite:25]{index=25}&#8203;:contentReference[oaicite:26]{index=26}. If the lexer ever merged or skipped newlines incorrectly, the parser might combine lines or break.
  - Keywords and literals: The grammar uses literal text for keywords like `decision`, `when`, `then`, `do`, `use`, `any`, `all`, etc., as well as operators `OR`, `AND`, `NOT`. The ANTLR-generated lexer (or our custom lexer) must correctly identify these. We should confirm that all needed keywords are either defined as lexer tokens or will be matched as literals. (For example, `any` and `all` might not have explicit lexer rules, but since they appear in parser rules, ANTLR will treat them as literal tokens automatically&#8203;:contentReference[oaicite:27]{index=27}. Our custom lexer should not accidentally classify them as a generic identifier; it should either defer to ANTLR’s literal matching or include them in a keyword list.)
- **Parser Error Handling:** The parser, built from the grammar, will naturally throw errors if the input token stream doesn’t conform to the grammar. We should ensure that common error cases (especially indentation issues) are caught as early as possible (in the lexer), but also handle any parser-level errors gracefully:
  - If the lexer emits an error token or throws an exception, the parser should not proceed blindly. We might integrate an error listener with the parser to catch syntax errors and report them in a user-friendly way.
  - Ensure that the parser can recover or at least fail clearly on unexpected input. For instance, if a line starts with an invalid keyword or if a structure is out of place, ANTLR’s default error messages may be cryptic. We might later customize error messages or use an `ANTLRErrorStrategy` to improve this, but that’s a future enhancement. For now, just verifying that the parser doesn’t hang or crash on bad input is sufficient.
- **Consistency with Updated Grammar:** Since the grammar was recently changed (for example, adding the `optionalQualifier` rule and the optional `compositeExpression` in `casefeature`), the parser code and tests must be updated to reflect these changes:
  - The lexer should handle new token sequences arising from these changes (e.g., the newline after an `any` qualifier, or parentheses around composite boolean expressions).
  - The parser tests (see below) currently illustrate correct usage of these new grammar features. The development team should use those as the baseline for what is “correct” and update the lexer or grammar further if any discrepancy is found (for example, if the parser test expects a certain parse tree for a given input but the current lexer doesn’t produce the needed INDENT tokens, that indicates a lexer bug to fix).
- **Integration Testing:** We should have at least one test that integrates the custom lexer with the parser end-to-end on a non-trivial input:
  - For example, parse a full `decision` with nested `when` clauses using the real lexer and parser together, and assert that the parse tree has the expected shape (e.g., a `decision` node with a child for each `whenClause`, etc.). This ensures that our components interoperate correctly.
  - Use example files from `src/examples` as test inputs for integration tests. These examples are likely more complex and closer to real use cases, which will validate the parser against realistic scenarios.
- **AI Assistance for Parser:** We can utilize AI tools in parser development too:
  - When grammar changes are needed, we can ask the AI to propose grammar rule modifications or to explain conflicts in grammar if we encounter them. This can speed up resolving tricky grammar issues.
  - The AI can help generate complex test scenarios for the parser. For example, “Generate a CRL snippet with three nested decisions using both `any` and `all` qualifiers” – the output can serve as a test input.
  - If parse errors occur, the AI can assist in diagnosing whether it’s due to lexer output or grammar mis-specification by analyzing the symptoms (though ultimately the devs will verify the cause).

## Testing Strategy and Format
Robust testing is vital for this project, given the complexity of indent-sensitive parsing. We will refactor and expand the test suite to ensure confidence in the lexer and parser. Tests should be **clear, organized, and comprehensive**. Key points for the testing approach:

- **Adopt Consistent Structure:** Follow Jest best practices for test organization to make tests easy to read and maintain. Use `describe` blocks to group related tests (e.g., a describe for Lexer tokenization, another for Parser behaviors, etc.)&#8203;:contentReference[oaicite:28]{index=28}. Within each group, use `it`/`test` blocks with descriptive names that state the expected behavior (e.g., *"should emit an INDENT token when a new block is indented"*, *"parser should recognize a 'decision' with nested 'when' clauses and produce correct parse tree"*).
  - For example, in `CRLLexer.test.ts`, we might have:
    ```ts
    describe("Indentation handling in CRLLexer", () => {
      test("emits INDENT and DEDENT tokens for a simple nested block", () => {
        const input = `if something\n    do "Action"\n`;
        const tokens = lex(input);
        // Expect token sequence: IF, STRING, NEWLINE, INDENT, DO, STRING, NEWLINE, DEDENT, EOF
        expect(tokenTypes(tokens)).toEqual(["IF","STRING","NEWLINE","INDENT","DO","STRING","NEWLINE","DEDENT","<EOF>"]);
      });
      // ... more tests
    });
    ```
    This structure makes it clear what aspect of the lexer we are testing.
- **Lexer Unit Tests:** Tests for the lexer should directly exercise the custom lexer’s output. For given input strings, verify that the sequence of tokens (by type and/or text) matches expectations:
  - Create helper functions in tests if needed, such as `lex(input: string) -> Token[]` to produce a token array from the custom lexer, and perhaps `tokenTypes(tokens) -> string[]` to map tokens to their type names for easy assertions.
  - Test various scenarios:
    - **Basic indent/dedent**: e.g., a single decision with one nested when, ensuring one INDENT and one DEDENT appear at the correct places.
    - **Multiple nested levels**: e.g., a decision with a when inside another when (two levels deep) to see multiple INDENTs and DEDENTs in sequence.
    - **Same-level sequences**: e.g., a decision with multiple sibling `when` clauses at the same indent level (should produce INDENT at the start of the block, then no additional INDENT for each sibling, but a single DEDENT at block end).
    - **Qualifiers**: ensure that when a `any` or `all` qualifier appears, it’s followed by a NEWLINE and then an INDENT for the nested conditions. Lexer should simply see `any` as a normal keyword token and the newline after it triggers an indent for the subsequent block.
    - **Terminal actions**: ensure that within an indented block, multiple `do` or `use` statements each on new lines do not produce extra INDENT (they are at the same indent). For instance:
      ```
      when "X" then
          do "Action1"
          do "Action2"
      ```
      should yield one INDENT before `do "Action1"`, then `do "Action2"` comes after a NEWLINE but at same indent (no new INDENT token), then DEDENT after. Lexer tests should catch that only one INDENT is emitted for the whole block, not per line.
    - **Comments and blank lines**: for example, a block where one line is just a comment or blank. Verify the lexer either skips it correctly or handles it without extra indent changes. E.g.:
      ```
      decision "Test"
          // comment
          when "Cond" then
              do "Act"
      ```
      should still produce a valid token stream with perhaps a NEWLINE for the blank comment line but no indent change.
    - **Error conditions**: Provide inputs with misaligned indents to ensure the lexer identifies the error. For instance, a dedent that doesn’t match any indent level:
      ```
      decision "Test"
          when "Cond" then
              do "Act"
     <--- (dedent only 2 spaces instead of 4)
      ```
      We expect the lexer to throw an error or produce an error token. The test should assert that an error is indeed raised for this input. Similarly, an input with indent of 6 spaces after an indent of 4 should error.
  - Compare expected vs actual token types rigorously. The parser tests may have examples of expected sequences that we can use as reference. We might also use snapshots for token sequences – for complex inputs, storing the entire token list in a snapshot can alert us if something changes unexpectedly. **However**, be mindful to update snapshots intentionally when grammar changes, not blindly accept changes.
- **Parser Unit Tests:** Tests for the parser (in `CRLParser.test.ts`) should focus on higher-level correctness of parsing:
  - Use the actual parser with the custom lexer (as in integration) to parse input strings or example files.
  - Verify that the parse tree or the outcome aligns with expectations. We can do this by:
    - Using ANTLR’s parse tree walker or the structure of context objects. For example, after parsing, check that `parser.getNumberOfSyntaxErrors() === 0` to ensure successful parse.
    - Use parse tree string representation: ANTLR’s `toStringTree()` can produce a parenthesized representation of the tree. We can compare that to an expected string (or use snapshot testing) if the tree structure is stable. For instance, parsing a simple rule might yield something like `"(file (statement ... ) (EOF))"` – tests can assert important parts of this string.
    - Alternatively, use the visitor/listener to gather semantics. For test simplicity, we might not need a full visitor yet, but could at least confirm the presence of certain nodes. For example, ensure that a `decision` rule produces a DecisionContext with the expected number of whenClauses inside it.
  - The parser tests should mirror many scenarios of the lexer tests (since lexing is half the story, parsing is the full story). For each important language construct, have a parser test:
    - Parsing a complete `decision` block with multiple conditions and actions (maybe using an example from `src/examples`).
    - Parsing an `action` definition and a `casefeature` definition to ensure these non-nested (single-level indent) structures are handled (they each have their own INDENT/DEDENT in grammar for the block of clauses like fhirtype, profileurl, etc. :contentReference[oaicite:29]{index=29}&#8203;:contentReference[oaicite:30]{index=30}).
    - Parsing a casefeature that includes a `compositeExpression` (the optional boolean expression in parentheses)&#8203;:contentReference[oaicite:31]{index=31}, to ensure that part of the grammar works (and that the lexer correctly handles the `(` and `)` as separate tokens, as well as the keywords `AND/OR/NOT`).
    - If the grammar allows multiple top-level statements in one file, test a file with e.g. a decision followed by an action to ensure the parser can handle consecutive statements separated by newlines.
  - Parser tests can also include **negative tests** where we feed known invalid input and expect the parser to report an error. For example, a `decision` without any `when` clauses (just "decision X" and EOF) should fail to parse – the test should confirm a syntax error occurs in this case. Or a `when` clause with no `then` keyword should error, etc. This ensures the grammar is enforcing rules as expected.
- **Using Examples in Tests:** We should particularly utilize the `src/examples` files in a test to ensure our language works on real examples:
  - Write a parameterized test that loads each example file, runs the parser on it, and asserts zero syntax errors. Possibly also assert that certain top-level constructs count matches (e.g., if we know the example contains 2 decisions and 1 action, after parsing we can count the occurrences of those contexts).
  - This gives confidence that the language features in examples (which might be more extensive than our unit tests) are all supported.
- **Test Maintenance with Grammar Changes:** As the grammar evolves, tests must be kept up-to-date:
  - When a new grammar rule or feature is added (e.g., a new kind of clause or a new keyword), add corresponding tests. For instance, if tomorrow we add an `otherwise` clause to a when-block, we’d write tests for that new syntax.
  - If grammar changes alter existing behavior (for example, changing indent size rules or making something optional that wasn’t), update the expected outcomes in tests. The tests serve as living documentation of the language – any change in language syntax or semantics should reflect in test expectations.
  - Use version control and CI to catch any failing tests after grammar changes. The CI pipeline should run all tests on each commit; if an AI tool is used to regenerate some code (lexer or parser), it should also run tests to verify correctness before changes are merged.
- **Refactoring Existing Tests:** The current lexer tests are said to be “formatted incorrectly.” We need to refactor them to align with standard structure and the current grammar:
  - Ensure that each test clearly isolates a single scenario and uses proper assertions (rather than, say, one test checking multiple things or printing output manually). Break them into multiple tests if needed.
  - Ensure they use the updated expected token names or values that match the new grammar. If, for example, the old tests expected a token type number or outdated token name, update them to use the current token definitions.
  - Align the style with parser tests. If parser tests use a certain pattern (like using a helper to parse and then checking the result), consider applying similar patterns in lexer tests for consistency.
  - Remove any ad-hoc printing or manual inspection from tests – they should be fully automated and assertion-based. The goal is that a developer can run `npm test` and immediately see which scenario failed and why, without additional interpretation.
- **AI in Testing:** AI assistance can greatly help in our testing efforts:
  - We can ask the AI to generate *many* variations of input (including edge cases) to augment our test cases. For example, use AI to produce a complex nested scenario mixing `any` and `all`, multiple siblings, etc., which we can include as a test input.
  - The AI can help convert informal examples or scenarios described in English into actual CRL code that we then test.
  - AI can also review our test descriptions and suggest missing cases. For instance, it might recognize we haven’t tested a certain combination of nested blocks and prompt us to add it.
  - When refactoring tests, an AI can quickly transform a block of tests to a new format (renaming tokens, splitting cases) following our instructions, which saves time but we must verify the changes are correct.

## Integration Points and Tooling
This section highlights how different parts of the system connect and how tooling (including AI tools) supports the development workflow:

- **Lexer-Parser Interface:** Ensure a clean interface between the custom lexer and the parser:
  - The custom lexer should implement the necessary interface/protocol that ANTLR’s `CommonTokenStream` and `CRLParser` expect. In practice, this means our lexer should subclass ANTLR’s `Lexer` base class (from the antlr4ts runtime) or mimic it. It should produce `CommonToken` objects with the correct token type values as defined by the ANTLR-generated `CRLParser.tokens` (if any).
  - We might consider an approach where the ANTLR grammar is split into a lexer grammar and a parser grammar. In that scenario, we would use a `tokenVocab=CRLLexer` option in the parser grammar&#8203;:contentReference[oaicite:32]{index=32}. If we do this, we need to maintain a dummy lexer grammar for ANTLR generation that defines all tokens (including INDENT/DEDENT as keywords or in a mode) but not the logic. This way, ANTLR generates token type constants and basic recognition for keywords, while our custom code overrides the actual lexing process. The requirement is to set up and maintain that correctly so that any new token in the parser grammar (like a new keyword) is also declared in the lexer token definitions.
  - If splitting grammar is too complex, we can keep a combined grammar but instruct ANTLR not to overwrite certain sections. Either approach is fine as long as the final token set and parser rules are consistent.
- **Build/CI Integration:** The project’s build process (npm scripts, CI pipeline) should integrate generation and tests:
  - The `generate` script should be straightforward to run and documented. After running it, a developer should know to run tests to ensure nothing broke.
  - On CI (continuous integration server), ensure that before tests run, the grammar is in sync. One strategy is to check in the generated code; another is to run the generator as part of CI. We need to decide and document this. If we go with checking in generated code, we must make sure developers don’t forget to regenerate. Perhaps add a CI step that regenerates and diff-checks against the repo to catch any discrepancies.
  - All tests (lexer, parser, integration) should be run in CI. If any test fails, that indicates either a bug or a needed update to tests following intentional grammar changes.
  - We should also include linting (for code and grammar, if possible) to maintain code quality. A formatting/linting step for the grammar file could catch inconsistent definitions or unused tokens.
- **AI Integration in Workflow:** Define how AI tools integrate into our development:
  - **Code Generation/Refactoring:** Use AI pair-programming assistants (like GitHub Copilot or ChatGPT in coding mode) for generating boilerplate or refactoring. For example, after writing a new grammar rule, we might prompt the AI to generate corresponding test cases or even a baseline implementation in the custom lexer if needed (though grammar-driven, the lexer might not need heavy changes for a new rule unless new indentation contexts are introduced).
  - **Research and Troubleshooting:** When encountering issues (e.g., a puzzling parser error or a complex grammar conflict), use the AI to gather information or solutions. The AI can quickly search known ANTLR patterns or suggest how others solved similar problems. (This requires feeding the AI sanitized error messages or code snippets; be mindful of any proprietary code when doing this.)
  - **Continuous Learning:** The AI could be used to keep us updated on best practices. For instance, if a new version of ANTLR or antlr4ts introduces a better way to handle indentation, the AI might help discover that. It can also help in understanding ANTLR’s error messages or in exploring how to implement the future compiler stage (by looking up patterns for writing compilers).
  - **Limitations:** We must also clearly state that AI is a helper, not an authority. All final decisions on code changes and merges lie with the development team. AI-suggested code will be reviewed in code reviews like any other contribution. We should also ensure any use of AI does not introduce licensing issues (only use it to generate code that we can legally use, and don’t inadvertently include large unattributed excerpts of external code).

## Future Extensibility and Compiler Development
Looking beyond the current lexer and parser, the ultimate goal is to develop a full compiler or interpreter for CRL. Our design and requirements should facilitate future extensions:

- **AST and Semantic Analysis:** Once the parser can produce a correct parse tree for CRL programs, we will introduce a semantic analysis phase:
  - Plan to create an **Abstract Syntax Tree (AST)** representation that is more convenient for semantic processing than the raw ANTLR parse tree. We can write ANTLR parse tree listeners or visitors to transform the parse tree into a well-structured AST (e.g., classes like `DecisionNode`, `WhenClauseNode`, etc., with properties for their subcomponents).
  - The current grammar is designed to capture necessary information (e.g., strings for names, the structure of conditions and actions). We should verify it has all info needed. If not, we might adjust the grammar (for example, labeling parser rule returns or adding more token information) to ease AST creation. This is easier to do now than later.
  - Ensure the lexer and parser preserve token text where needed (for example, the text of `STRING` tokens, which represent user-defined identifiers or values in quotes, should be accessible in the AST nodes).
  - We will implement semantic rules in the compiler phase (like ensuring that a `use "X"` references a defined `decision` or `action` named "X", if such a rule exists in the language). The groundwork for this is that the parse tree cleanly separates those references – which it currently does by treating them as `STRING` tokens. We might later introduce distinct token types for certain identifiers to differentiate them (if needed for clarity in AST).
- **Compiler/Code Generation:** Depending on what “compiler” means for CRL (perhaps compiling into some executable form, or translating the CRL rules into another language or runtime logic), we should design the system to allow plugging in a backend:
  - The backend compiler might take the AST and produce output such as JavaScript code, a JSON representation of the rules, or even direct execution of the logic. We should keep the possibility open.
  - Ensure that our code is modular: the lexer and parser are the **frontend** (producing a parse tree/AST), and the compiler will be the **backend**. They should communicate via well-defined data structures (the AST). This means we avoid entangling parsing logic with what we will do with the data. For example, do not attempt to produce output during parsing; first fully parse into an AST, then separately traverse the AST for output.
  - File organization for the compiler: likely we will create `src/compiler/` to hold AST definitions, semantic analyzer, and code generation logic. This separation should be planned for. The requirements here are to keep the code structured such that adding this directory and code will not require big changes to the existing lexer/parser (they will remain largely the same, just we add new consumers of their output).
- **Extending the Grammar:** The language may gain new features (and indeed has recently changed). Design choices now should make adding new grammar rules easier:
  - If a new block structure or syntax is added that is also indentation-based, our lexer should be able to accommodate it with minimal changes. For example, if we later add an `otherwise` clause that works like an `else` after all `when` clauses, we would add a grammar rule for it (with the same indent/dedent structure) and the lexer’s existing indent logic should naturally handle it (since it just reacts to indent changes, not specific keywords). We might only need to update tests for the new construct.
  - If new keywords or token types are introduced, we must add them to the grammar and ensure the custom lexer recognizes them appropriately. This might involve updating the dummy lexer grammar or token list we maintain.
  - We should avoid hard-coding things in the lexer that depend on specific grammar sequences (the lexer should ideally not need to know “after a ‘then’ token, I expect an indent” – that’s the parser’s role). Instead, the lexer just follows the generic rule of indentation, making it generic enough to support new syntactic constructs without modification. This separation of concerns will make future grammar extensions less error-prone.
- **Testing Future Features:** As we extend toward a compiler, our testing should also extend:
  - We will introduce **semantic tests**: for example, if the compiler is supposed to output some code or perform actions, we’ll test that given a CRL input, the correct output or effect occurs. This is outside the current scope but worth planning for. It means our current tests focusing on structure will be complemented by tests focusing on semantics and end results.
  - Continue using AI to generate complex scenario tests as the language grows. As more features combine, the state space of possible programs grows; AI can help suggest interesting combinations to test that we might not manually think of (like deeply nested conditions with multiple actions, etc.).
  - Documentation as tests: we might consider writing example-based documentation (like a README with CRL examples) and ensure those examples always remain valid by testing them. This keeps the language user documentation in sync with the implementation.

- **Performance and Scalability:** As the compiler develops, performance might matter if CRL files become large. Our current requirements for the lexer and parser focus on correctness, but we should keep an eye on efficiency:
  - The custom indentation logic should be efficient (it likely is linear in the length of the input, which is fine). We just ensure no pathologically slow behavior (AI can help do a quick complexity analysis or generate large input to test performance).
  - ANTLR’s generated parser is typically efficient for deterministic grammars. If we notice performance issues, we might tweak the grammar (e.g., left-factoring if needed, though current grammar looks straightforward).
  - We should also ensure memory usage is reasonable (not retaining too many objects unnecessarily). This is not a pressing requirement now, but a consideration for the future when compiling many rules.
- **Maintainability and Team Knowledge:** Future developers (or even the AI assistant in the future) should be able to understand the system:
  - Keep the grammar file well-commented (as it currently is, explaining rules and their purpose)&#8203;:contentReference[oaicite:33]{index=33}. Update comments when grammar changes.
  - Keep the custom lexer code commented, especially the tricky parts of indent logic. This will help when someone needs to modify it to support a new scenario.
  - We might eventually auto-generate parts of the compiler (if, say, we describe the semantics in a higher-level way). AI might help in generating visitor code for each grammar rule, etc. Having clear structure now (like one context class per grammar rule) will make such generation easier.
  - Encourage contributions (human or AI) to follow the established patterns: e.g., all new tests should adhere to the style guidelines we set, all new grammar should come with accompanying tests, etc.

By following these requirements, the team will create a solid, test-driven foundation for the CRL language tooling. The combination of a careful custom lexer, a well-defined ANTLR grammar, and comprehensive tests (with AI support for rapid development) will ensure that as CRL evolves, the lexer/parser can evolve with it confidently, eventually enabling a full compiler implementation.
