# Supervised codification Codespace pilot

Status: **integration draft**, 2026-10-11. CRL is the cross-project design and decision point; KELP, Automation, Spaces, and the KE pipeline owner retain implementation responsibility for their components. This record separates agreed direction, released capabilities, proposals, and open acceptance work. ## Decisions and scope

- **Human-supervised run.** An operator prepares a batch from a loaded KELP artifact. A separate codifier later Locks the canonical artifact and works in a Nautilus-image Codespace on the prepared `<artifact branch>-nautilus` branch. Claude Code chat runs at that checkout root; no second KE-agent worktree is required. The project states and filters are defined in [WORKFLOW.md](WORKFLOW.md).
- **Pilot target.** The source-only `smile-digital-health/smile-demo-codification` repository now has canonical `artifact/auto-bleph` and prepared candidate `artifact/auto-bleph-nautilus`. The existing `smile-demo` deployed bleph encoding stays untouched. The prepared branch is an integration candidate, not a qualified Codify launch or clinical artifact.
- **Source.** Intake uses only the committed L34194 source snapshot from `smile-demo` commit `7a2b7f2de63fc441dba99ceed2b4aa57eb32a2dc`: `L34194-v27-2025-10-16.html` SHA-256 `0cd904938597f99bf05d9dfc86209c8e3d34dada1107ddd802dc04b680db6357`; text extract `.txt` SHA-256 `de332387e3a1bb3fb6720f592677eedef7ea988cd112917d087debb82a387e6f`; `.metadata.json` SHA-256 `684b35d673824695a1e78772c00185d2ebbe90c59375a4c6925d1f9cda3660a7`. The source-only canonical artifact contains those byte-exact files. The metadata's embedded hashes differ from the committed bytes; record that discrepancy without altering either. Prior `smile-demo` refined-source, anchor-source, provenance and encoded artifact files remain excluded from author input.
- **Pipeline seed.** The candidate reusable narrative package lives in [pipeline-candidate](pipeline-candidate), derived from the IEHP create-new mechanics without IEHP customer rules. Install the selected `.claude/` and `.vibe-tools/` payload only on `<artifact branch>-nautilus`; commit root `tmp/` scratch skeleton and the run record there. Canonical `artifact/auto-bleph` retains source and, after SaveCodify, only reviewed Codify output paths. The candidate still needs an approved Smile profile and real image/reviewer qualification.
- **Selection authority.** The Nautilus orchestrator freezes the selected pipeline, profile, source and output-scope identities in a versioned run record on the prepared branch before launch. No in-Codespace pipeline picker or KE override. A changed binding or source requires an explicit new revision and affected evidence recheck; the run record must not be treated as authorization while the package or lifecycle gate remains unqualified.
- **Version rule.** Pin both selected devcontainer paths and image digests, CRL/kit/engine/driver/MCP, KELP, Automation, agent/reviewer artifacts, pipeline package and profile to the run. Promotion of newer images/packages affects new runs, not active ones. A surviving stopped Codespace can resume on its original image within its retention period. Recovery after deletion is unproven until a per-run ref is demonstrated.
- **Runtime boundary.** The initiating workspace is a Codespace on the KELP image, where the user searches, Locks, opens the Codify card and later returns to Unlock/Complete. The separate authoring Codespace uses the Nautilus image and runs the supervised KE lead. They are distinct Codespaces because their images and roles differ. Nautilus' operator and orchestrator prepare batches and artifact branches; the user-facing Nautilus launch creates or opens the authoring Codespace under the codifier's account. Spaces helps stage both pilot image configurations, but no Spaces service or operator participates when a batch is created or launched. Long-term ownership of the Nautilus image remains undecided.
- **Handoff and identity.** Follow [WORKFLOW.md](WORKFLOW.md): KELP Add enters Ready to codify, from which a codifier may directly Lock and work without Nautilus. For initial assisted preparation, Nautilus writes Nautilus in progress at batch start and Nautilus staged at batch completion to the canonical artifact Project item; a subsequent Codify-card Lock sets Codify in progress. An earlier-card Lock opens or reuses a rework subtask and leaves the advanced parent unchanged. Nautilus launches a separate Codespace on the exact suffixed branch, supports SaveCodify there, and returns the user to the initiating KELP workspace for refresh, Unlock and separate Complete codify. KELP owns its entity lifecycle and KELP-origin Project transitions; Nautilus owns batch preparation, its two Project transitions and filter, launch, and assisted Codify file delivery. Both share the canonical artifact Project item and Status field on the initial path; placement of assisted rework statuses remains open. Nautilus maintains its run/assignment identity without a new shared pass-ID protocol.

## KELP intake and permissions

For the pilot, KELP Add took the original HTML as primary source; an authorized content editor then locked source, added the text extract and metadata as companion files, Saved source, and released the source lock. Do not hand-edit `.kelp` records. That intake is observed; the revised target workflow makes Add enter Ready to codify, but current KELP did not apply that status. Batch start must verify the complete three-file source snapshot.

KELP Add writes the initial scaffold across configured and reserved entity folders, root `package.json`/`.npmignore`, and `.kelp/produced/source.json`; source-folder-only path permission is insufficient. Lock/Save/Release also modify `.kelp` and selected entity folders and require fetch/push to the artifact branch. Git author email governs lock ownership; GitHub authentication and repository rules govern write access. Spaces/repository administration chooses actual team memberships; KELP specifies no `ke` team.

KELP can configure the eight Codify scopes and the review/MV entities. The target state/filter transitions are in [WORKFLOW.md](WORKFLOW.md). Add enters the preparation queue even if companion source intake still needs completion; Nautilus checks that intake before batch start. Direct Codify may start without Nautilus, and an assisted run may start after Nautilus preparation. `Lock from=card` takes the ordinary entity locks. If that card is earlier than the parent's current configured stage, KELP opens or reuses its rework subtask without advancing the parent; otherwise it writes the card's configured in-progress status to the parent. `Unlock from=card` releases the locks and completes the matching rework subtask once that card's locks are released. Explicit Complete performs the card's configured next-ready handoff. On the normal path it moves the parent; after earlier-card rework, whether it moves the parent or creates linked next-stage work remains unresolved. The assisted route uses SaveCodify; direct canonical work uses KELP Save where changed entities need delivery. KELP preserves Nautilus-written preparation statuses on ordinary refresh. The placement of Nautilus preparation statuses during earlier-stage assisted rework remains an explicit design decision; the first release must not overwrite the advanced parent merely to display preparation. A simple re-read and reconciliation at action boundaries suffices; no distributed transaction coordinator is required. Project stages derive from built-in and configured card actions, not a provider-specific workflow.steps layer.

For interim image and lifecycle staging under KELP 0.12, use the released eight-scope Codify/Nautilus card while qualifying the remaining Project and Complete controls. The card and command smoke do **not** pass the full Project, Lock/Save, Codespace or clinical workflow. KE/MV entities and lenses remain in the graph throughout.

The pilot repository and byte-exact source-only `auto-bleph` artifact now exist. Spaces must stage and qualify the initiating KELP image and separate Nautilus authoring image on the existing repository. Batch preparation occurs on the exact suffixed branch; the canonical artifact is the only KELP Lock target. Verify source, branch, image, provider and permission identities during the moderated test.

Spaces reports a registry gap: it currently pins one image per target, while this repository needs a different digest for each devcontainer configuration. Its interim authoring image without Nautilus may prove layout, receipts and lifecycle; the full pilot requires the KELP image with Nautilus's launcher and the separate Codify image with the complete Nautilus pipeline and reviewers. Neither interim image evidence nor a devcontainer path alone proves the effective authoring image. Verify the in-Codespace image manifest and startup receipt before authoring.

## Launch, readiness and evidence

### Codify image and authoring checkout

The CRL/KE pipeline owner defines the authoring workflow and its tool requirements; Nautilus owns launch and any needed in-Codespace binding/resume; Spaces builds and verifies the image and devcontainer selection. The **Nautilus image** must provide the Claude Code VS Code extension as the human-supervised authoring chat, CRL with callable tools, KELP with callable lifecycle tools, Vibe Tools with the configured independent reviewer arms, and the pinned Java/Node/Python/Git dependencies used by the selected pipeline. Nautilus's VS Code extension is required in the initiating KELP image for launch; its presence in the authoring image depends on Nautilus's actual implementation. A Nautilus CLI/MCP may support authoring admission if needed. Codex extension or CLI may support a reviewer arm if that arm requires it; neither replaces the Claude Code authoring entrypoint. Installed extensions alone do not establish callable tools: exercise the actual Claude Code session, CRL, KELP and both review arms.

The authoring Codespace has one checkout of the content repository at `<artifact branch>-nautilus`. The selected `.claude/` and `.vibe-tools/` pipeline and root `tmp/` scratch live on that prepared branch. The canonical branch receives only reviewed Codify output through SaveCodify; it never receives the prepared branch's pipeline or scratch ancestry. The image supplies pinned executables and extensions, not a per-policy Git checkout.

KELP acts on the canonical artifact branch only. The prepared branch is excluded from KELP artifact discovery by a generic eligibility rule; its `.claude/`, `.vibe-tools/`, `.nautilus/` and root `tmp/` are not Codify delivery paths. Nautilus reviews exact dirty files and delivers only an approved output-file allowlist. The initiating KELP Codify card owns and enforces Lock before it invokes Nautilus; the authoring checkout does not treat its local status as canonical lifecycle proof.

Run evidence stays on the prepared branch and its durable run record/ref, linked to the delivered canonical commit. Before deleting the authoring Codespace, verify the remote record and delivery, and resolve intentional local edits that SaveCodify excluded. The initiating canonical checkout refreshes before KELP Unlock. No second Codespace checkout or whole-branch merge is needed.

**Publish must leave `.claude/`, `.vibe-tools/`, `.nautilus/` and run evidence out of `main` and its new ancestry.** The prepared branch never merges wholesale into canonical; SaveCodify produces a canonical-only-parent output commit. Validate the intended artifact entities, required KELP metadata and absence of pipeline ancestry before Publish. Current publication safety and human authorization gates remain independent of project status; the first auto-bleph pilot need not Publish.

Before the first launch, qualify Nautilus's configured KELP action and command provider in the **initiating KELP-image Codespace** on `smile-demo-codification`. It reads that repository's Codify card. The separate authoring Codespace must use the **Nautilus image**, selected explicitly at creation; Nautilus then verifies the effective image before authoring. A Nautilus VSIX present only in the future authoring Codespace cannot open the card on the first click.

No current KELP or Nautilus build is claimed to implement the complete sequence.

It permits test Codespaces on each image; effective installed identities and the selected authoring devcontainer path are verified after provisioning. Neither step alone is full qualification.

The Codespaces VS Code server is supplied by the platform; check it against extension `engines` rather than claiming to pin it. Nautilus verifies installed bytes again at each agent launch and writes a later assignment/pipeline/profile and agent/reviewer receipt. Promote required receipts to durable storage before deleting the Codespace. The pipeline supplies representative CRL/KELP smoke evidence. No single installed-file check is the whole readiness signal. `kelp check` is one component, not overall readiness. Fetch/push/path permissions and a full lifecycle acceptance exercise require a separate authorized test. Do not bake secrets or treat installation hashes as proof that agents can work.

Spaces reports that the security white paper is the target, not the pilot admission gate. For this trusted-staff pilot, default-deny/fail-closed egress and no passwordless sudo remain tracked backlog #5 and #6. Record actual reachable destinations and deviations; do not claim white-paper compliance. Keep the image self-contained with no runtime package or MCP downloads, disable built-in VS Code AI (`chat.disableAIFeatures=true`), pin/check effective installed bytes, and use each user's repo-scoped Codespaces secrets rather than baked or shared credentials. The agent, reviewers and pipeline must operate within the measured pilot environment. Later image hardening must preserve the Nautilus workflow.
