# Source-to-tree interview for fresh medical-policy encoding

First inventory separately answerable conditions and their source relationships. Then draw the tree in source language; only afterward translate it into CRL. Preserve meaningful groups and parent-child edges. Use a supplied Request as the first decision condition, separate request branches if source scope requires them, a source-authorized EIU condition before ordinary eligibility when applicable, and a strongly depth-oriented main eligibility flow. A named population/applicability group can be a Criterion when it makes source meaning inspectable. Boolean AND/OR is appropriate within a coherent group or Decision guard when it preserves meaning; grouping may present questions together. A Criterion is not a way to put the entire ordinary interview into one box. A single-operand wrapper with no meaning beyond its operand adds nothing.

For an ordered `first` branch, an unanswered reached guard can pause before a later alternative. For a grouped Boolean expression, `A OR B` can be true with A missing and B true, but both questions may appear together. Identify which behavior the source and chosen interview require; do not claim one construct has the other's behavior. Keep absence distinct from an explicit No and errors distinct from both. Do not use an all-answers completion Criterion merely to force unrelated questions to be asked.

At every terminal, check exact configured activity, source support, missing-answer behavior and whether another route changes question relevance. The source and explicitly approved customer binding determine answer choices and any uncertainty behavior. Retained current answers and correction access are checked through native returned Q/QR, not by client reconstruction of missing state. The client may prune for convenience, while an unpruned standards-compliant submission must still evaluate correctly.
