# CPGL Grammar Project – Updated Lexer Requirements Documentation

This document outlines the comprehensive requirements for updating the CPGL project to remove the custom whitespace‐controlled lexer, transition to using the autogenerated ANTLR lexer, and update unit tests and any dependent components (e.g., validator) to work with the new grammar definition.

---

## 1. Introduction

The CPGL project originally implemented an ANTLR grammar with a custom lexer to manage whitespace sensitivity. Recent updates to the CPGL grammar now enable the grammar to be whitespace-insensitive, eliminating the need for a custom lexer. This document specifies the requirements for removing the custom lexer, integrating the autogenerated lexer, and updating all associated tests and validation tools.

## 2. Objectives

- **Remove Custom Lexer:** Eliminate the custom lexer code and all associated support components.
- **Integrate Autogenerated Lexer:** Update the project configuration and build scripts to use the auto-generated lexer from the current ANTLR grammar definition.
- **Update Test Suite:** Adapt existing unit tests (originally written for the custom lexer and parser) to conform to the new grammar and the autogenerated lexer.
- **Validate Project Functionality:** Ensure that the parser, validator, and integration tests are updated to reflect the changes, and continue to verify the accuracy of the CPGL language processing.

## 3. Scope

- **Codebase Cleanup:** Remove all custom lexer implementations and any test cases that depend solely on that lexer.
- **Project Build:** Adjust build configuration and scripts to generate and use the ANTLR autogenerated lexer.
- **Unit & Integration Testing:** Revise unit tests for the lexer and parser so that they align with the new grammar specification; review and update validator tests if applicable.
- **Documentation and README:** Update project documentation, developer guides, and auto-generated README files to reflect changes in lexing and parsing infrastructure.

## 4. Functional Requirements

### 4.1 Removal of Custom Lexer
- **Code Removal:** All custom lexer source files, utility classes, and configuration files specific to the custom whitespace-controlled lexer must be removed.
- **Dependency Update:** Remove any dependencies (libraries, modules) that are solely used for supporting the custom lexer.

### 4.2 Integration of Autogenerated Lexer
- **ANTLR Configuration:** Ensure that the current ANTLR grammar (CPGL.g4) is set up to generate both the lexer and parser, with the lexer now being whitespace-insensitive.
- **Build Script Updates:** Modify build scripts (e.g., Maven, Gradle, or custom scripts) so that they automatically generate the lexer from the updated grammar.
- **Code Integration:** Update project initialization and runtime code to utilize the autogenerated lexer instead of the removed custom lexer.

### 4.3 Update of Unit Tests
- **Lexer Tests:** 
  - **Removal:** Eliminate or refactor unit tests that specifically verify custom lexer behaviors no longer applicable.
  - **Adaptation:** Update remaining lexer tests to validate that the auto-generated lexer properly tokenizes input as defined by the new grammar.
- **Parser Tests:**
  - **Revision:** Update parser tests to align with the updated grammar and lexer output.
  - **Coverage:** Ensure that tests cover the full spectrum of CPGL language constructs using the new tokenization (e.g., decisions, activities, concepts, and terminology statements).

## 5. Non-functional Requirements

- **Performance:** The autogenerated lexer should perform at least as well as the custom lexer in terms of speed and resource usage.
- **Maintainability:** The new solution should simplify future maintenance by leveraging the standard ANTLR-generated lexer.
- **Documentation:** All changes must be clearly documented both in code comments and in the project documentation (README, developer guides).
- **Consistency:** The updated tests and validator must consistently reflect the behavior of the new grammar, ensuring that no backward compatibility issues arise for valid CPGL text samples.

## 6. Testing & Validation

- **Automated Testing:** All unit tests and integration tests should be executable via the existing continuous integration pipeline.
- **Regression Testing:** Ensure that previously passing tests for the custom lexer (where applicable) are either removed or have equivalent tests covering the autogenerated lexer.
- **Manual Verification:** Conduct manual tests using sample CPGL texts (including edge cases) to confirm that the parser and validator behave as expected.
- **Test Coverage:** Aim for high test coverage for all significant grammar constructs, especially edge cases related to whitespace sensitivity.

## 7. Dependencies and Constraints

- **ANTLR Version:** Ensure that the correct version of ANTLR is used to generate the lexer and parser.
- **Build Tools:** Update and verify configuration for Maven/Gradle or any other build system used in the project.
- **Project Integration:** Ensure that any external tools or downstream systems that consume CPGL parsed output are not adversely affected by these changes.

## 8. Acceptance Criteria

- **Successful Removal:** The custom lexer and its dependencies are completely removed from the codebase.
- **Build Success:** The project builds successfully with the autogenerated lexer and parser from the updated grammar.
- **Passing Tests:** All updated unit tests (lexer, parser) pass against a comprehensive suite of CPGL texts.
- **Documentation:** Updated documentation reflects the new infrastructure and provides guidelines for further development.
- **Stakeholder Approval:** The updated system is reviewed and approved by project stakeholders and domain experts based on functionality and test outcomes.
